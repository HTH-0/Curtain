# 입력 정규화 측정 결과 (우회 세트 v2, 블라인드 v3)

측정일: 2026-11-04. 기준: [spec.md](../../spec.md) FR-13(AC-13.1~13.11). 비교: 정규화를 넣기 전 코드(커밋 `1066460`)와 넣은 뒤 코드(커밋 `45b2865`)를 같은 세트로 쟀다. 세트와 코드는 측정 전에 [freeze_v2.json](../set/freeze_v2.json)에 해시로 동결했고(`freeze_v2.py verify`로 같은지 확인한다), 결과를 보고 규칙과 세트를 바꾸지 않았다. 원자료는 `norm_v2/`에 있고 모두 가짜 데이터이다. 합격 기준은 두지 않았다(AC-13.3만 예외).

## 요약

- **회귀 없음(AC-13.3 충족).** 평가 세트 v1 596문장의 X, Y, 처리 정확도(552 / 596), 틀린 문장 목록이 이전 코드와 모두 같다. 정상 오탐은 0 / 106이다.
- **규칙을 만들 때 알던 유형(v2):** 변형 480문장의 탐지가 26.2%에서 79.8%로 올랐다(윌슨 95% 구간 23~30%에서 76~83%). 변형하지 않은 대조 120문장은 둘 다 100%이다.
- **처음 보는 변형(블라인드 v3):** 변형 240문장의 탐지가 12.1%에서 48.3%로 올랐다(구간 9~17%에서 42~55%). 정답 구간을 완전히 덮은 비율은 47.1%이다.
- **두 수치의 차이가 낙관의 크기이다.** 규칙 작성자가 유형을 아는 v2(79.8%)와 모르는 v3(48.3%)는 31.5%p 차이가 난다. 실제 공격자의 변형에서는 v3 쪽이 더 믿을 만한 값이다.
- **누출(정답 구간을 완전히 덮지 못한 변형):** v2에서 480문장 중 97개, v3에서 240문장 중 127개이다. 놓치거나 일부만 가려서 값이 외부로 나간다.
- **오탐:** 정상 유사 52문장 중 이전 코드 0개, 새 코드 2개이다(아래 설명). 평가 세트의 정상 106문장에서는 0개이다.
- **지연:** 탐지 시간(`detectMs`)의 중앙값 0.0ms, 95번째 백분위 1ms로 이전 코드와 같다(AC-13.7).

### 정상 유사 세트와 회귀

정상 유사 문장 52개 중 오탐(가림이나 차단)은 이전 코드 0개, 새 코드 2개이다(3.8%, 구간 1~13%).

- **benign-019는 실제 오탐이다.** 은행 표시("신협") 뒤 20자 안에 구분자 없는 10~14자리 숫자가 있으면 계좌로 본다(AC-13.4). 우체국만 송장번호 때문에 뺐고, 그 밖의 번호(응모번호, 영수증 번호)는 같은 규칙에 걸린다.
- **benign-043은 의도된 탐지에 가깝다.** 문장이 고객사 이름 `다온로지스`를 글자마다 띄어 쓴 것이라 AC-13.5가 찾도록 만든 모양이다. 이 문장을 정상으로 분류한 것은 세트 작성 쪽의 잘못이다. 동결 뒤라 세트를 고치지 않고, 오탐 수는 2개로 그대로 두되 실질 오탐은 1개로 읽는다.

## 놓친 것

- **범위 밖으로 정한 유형(AC-13.6)은 그대로 놓쳤다.** v2에서 이메일 `at` 표기 3종, 키 쪼개기 2종, 접속 문자열 스킴 변형 2종, JWT 점 뒤 공백은 모두 0%이다.
- **v2의 나머지 미탐:** 소문자 API 키 4개(AWS 키 규칙은 대문자만 본다. 이전부터 있던 한계), 두 글자 단어 `극비`를 글자마다 띄어 쓴 2개(오탐을 막으려고 세 글자 이상만 찾도록 한 설계이다), 하이픈 없는 값 1개.
- **v3에서 새로 드러난 빈틈**(아래 사례는 모두 새 코드가 놓쳤다):
  - 쪼개기 35개 전부: 줄바꿈으로 나눈 값(`010\n0100\n7946`, `010-\n1862-\n5264`).
  - 구분자: `010/1732/2870`, `010 - 6535 - 2334`처럼 하이픈 앞뒤 공백, `610922_2611800`의 밑줄, 슬래시.
  - 문자 바꾸기: 영문 대문자 `O`와 소문자 `l`을 숫자 대신 쓴 값(`O1O-O1OO-7946`).
  - 인코딩: 퍼센트 인코딩(`%30%31%30…`), HTML 엔터티(`&#48;&#49;…`). 24개 중 6개는 일부만 맞아 탐지됐으나 완전히 덮은 것은 3개이므로 나머지는 일부가 외부로 나간다.
  - 표기: 국가 번호(`+82 10-0100-7946`), 이메일 `[at]`, ` at `, `(at)`, 한글 숫자를 두 글자씩 묶은 값(`영오구팔-사사-영구사육이영육`, 한글 숫자는 세 글자 이상 이어질 때만 바꾸기 때문이다).
  - 사전 단어 속 공백 자리에 보이지 않는 문자를 끼운 `프로젝트​해솔`(사전 단어에 공백이 있어서 정규화로 공백이 사라진 모양과 맞지 않는다).

## 한계

1. **v2 수치는 낙관적이다.** 규칙을 만든 쪽이 변형 유형을 알고 있었고, 같은 생성기가 만든 문장이다. 값이 새로울 뿐 유형은 v1과 같다. 일반화의 정도는 v3를 보아야 한다.
2. **v3는 완전한 독립 시험이 아니다.** 서브에이전트 한 번의 호출로 만들었고, 같은 계열의 모델이다. 실제 공격자의 변형을 대표하지 않는다. 값은 60개이고 항목당 20문장이며, 유형별 문장 수가 19~54개로 고르지 않다. 눈으로 확인한 표본은 20개이다.
3. **정상 유사 세트는 일반 오탐율이 아니다.** 규칙을 아는 쪽이 오탐이 날 만한 곳을 찾아 쓴 52문장이다. 한 문장은 분류가 잘못되었다(위 설명).
4. **v3의 사례를 본 뒤에 규칙을 고치면 v3로 다시 잴 수 없다.** 개선은 새로운 블라인드 세트(v4)를 만들어 다시 잰다.
5. **두 서버를 같은 컴퓨터에서 동시에 돌렸다.** 지연 값은 참고용이다. 이전 코드는 `git archive 1066460`을 별도 폴더에서 빌드한 것이다.

## 후속 개선 후보 (이번 결과로 바로 고치지 않는다)

- 구분자 확대: 슬래시, 밑줄, 하이픈 앞뒤 공백, 줄바꿈, 국가 번호 `+82`.
- 숫자 모양의 영문자(`O`, `l`, `I`)를 숫자로 보는 정규화(오탐 위험이 커서 검증 규칙과 함께 검토).
- 퍼센트 인코딩과 HTML 엔터티 해독(해독한 사본을 탐지에 쓴다).
- 한글 숫자 두 글자 묶음 처리, 이메일 `[at]` 같은 표기 정규화.
- 은행 표시 뒤 구분자 없는 숫자(benign-019)의 오탐을 줄이는 조건(예: 숫자 앞 단어가 "응모", "영수증", "송장" 등).
- 모두 새 블라인드 세트로 효과와 오탐을 함께 잰 뒤에만 채택한다.

## 재현

```powershell
# backend/scripts에서. 서버 두 대(이전 코드 8081, 새 코드 8080)를 측정 모드로 띄운 뒤
python measure.py --input ../../docs/eval/set/bypass_v2.jsonl --out new_bypass_v2.json --base-url http://localhost:8080
python norm_report.py --dir ../../docs/eval/results/norm_v2 --out tables.md
python freeze_v2.py verify --freeze ../../docs/eval/set/freeze_v2.json
```

세트는 `build_bypass_set.py --seed curtain-bypass-v2 --replicates 10`, `build_benign_set.py`로 다시 만들면 같은 파일이 나온다. v3는 서브에이전트가 만든 변형이 필요하다. 입력, 변형 원본, 프롬프트를 [../set/v3_source/](../set/v3_source/)에 보존했고, `python build_blind_set.py assemble --inputs v3_input.json --variants v3_variants.json --out bypass_v3.jsonl`로 같은 세트를 다시 만든다.
